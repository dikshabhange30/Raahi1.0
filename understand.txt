## Raahi Backend Architecture — Basic Understanding

### 1. Authentication

Authentication answers: **"Who is this user?"**

Raahi registration creates an account using basic account information such as username, email, and password.

The email must be verified using an OTP before the account is considered verified.

Login accepts either:

* Username + password
* Email + password

After successful login, the backend provides a JWT access token.

### 2. Authorization

Authorization answers: **"What is this authenticated user allowed to do?"**

Examples:

* A normal user cannot create communities.
* Only the admin can create/manage communities.
* A user cannot access another user's private data without permission.
* Community membership must follow eligibility rules.

### 3. Account vs Profile

An account contains information required for authentication and account management.

A profile contains information about the person within Raahi, such as gender, city, profession, languages, bio, and profile image.

The profile can be completed after login.

### 4. Immutable Gender

Gender is an important profile attribute because it affects community eligibility.

Once a user selects their gender, the backend will not allow the user to change it through the normal API.

This rule must be enforced by the backend, not only by the frontend.

### 5. Community Eligibility

A user's gender determines which communities they are allowed to join.

For example:

* Male → Male or Unisex communities
* Female → Female or Unisex communities

The backend performs the final eligibility check.

### 6. Admin

Raahi has one administrator who manages the application from protected backend functionality.

The admin can:

* Create/manage communities
* Moderate users
* Review reports
* Handle feature requests

Admin functionality does not need to be exposed as a normal frontend feature initially.

### 7. User Safety

Users can block other users and report inappropriate behavior.

Blocking affects what users can do with each other.

Reports are stored so the administrator can review and take action.

### 8. Main Raahi Modules

* Authentication
* User/Profile
* Communities
* Community Membership
* Help
* Messaging
* Blocking
* Reporting
* Notifications
* Admin/Moderation
* Feature Requests

### 9. High-Level Flow

Registration
→ Email OTP verification
→ Login
→ JWT authentication
→ Profile completion
→ Community discovery
→ Eligibility check
→ Join community
→ Help / Messaging / Community interaction
→ Block / Report when necessary
→ Admin moderation when required

Why routers/?

We don't want to put every endpoint inside main.py.
Instead : 

main.py -> application setup

routers/auth.py -> authentication endpoints

routers/users.py -> user/profile endpoints

routers/communities.py -> community endpoints



The __init__.py makes routers a Python package and keeps imports predictable.




routers/ is a section/category for API endpoints. Each router file groups endpoints belonging to one responsibility:

routers/
│
├── auth.py          → registration, login, OTP
├── users.py         → profile, user-related operations
├── communities.py   → community operations
├── messages.py      → messaging
├── reports.py       → reports
└── admin.py         → admin-only operations




Remember this order  ::::::::::

imports ->  create FastAPI app ->  database setup ->  include routers -> define endpoints



if we're changing the database structure, create_all() will create the new table when the application starts.

services/?
Think of it as the place for business logic that an endpoint needs but shouldn't contain directly inside the router.




Resend: A transactional email service that allows our Raahi backend to send emails programmatically.
 We will use it to send the email verification OTP to a user's email address during registration.
 The Raahi backend communicates with Resend using an API key, while the API key remains private in .env.


 ** JWT : create_access_token

 Think of JWT as a temporary digital pass.
 username + password -> valid -> JWT token -> client stores token -> sends token with future requests -> backend knows "who is this?"

 What is a JWT secret key?
The JWT secret key is a private secret that only your backend knows.
 Your backend uses it to cryptographically sign JWT tokens, so later it can detect if someone has modified or forged a token.

 Login successful - >  Backend creates JWT - >  JWT + SECRET KEY → signed token - >  User receives token
 later 
 User sends JWT -> Backend checks JWT using SECRET KEY -> Valid signature? → ✅ trust the token Invalid signature? → ❌ reject it
